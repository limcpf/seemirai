# PRD

## 1. 개요

- 제품 이름: Seemirai
- 한 줄 설명: Upbit KRW 현물에서 비용 차감 후 기대값이 남는 거래만 paper trading으로 검증하는 자동 주문 엔진
- 핵심 가치: 좋은 매수 시점을 찾는 것보다 거래소 수수료, 스프레드, 슬리피지, 펀딩비, 유동성 리스크를 이긴 거래만 남기는 것
- 현재 단계: M8-C 완료. Upbit KRW 현물 paper trading MVP 구현과 24시간 public WebSocket soak 검증을 닫았고, 반복 운영은 M9 paper 운영 베타에서 진행한다.

## 2. 문제 정의

### 사용자가 겪는 문제

- 암호화폐 시장은 24/7로 열려 있어 장 마감 기준 정리보다 상시 감시와 자동 정지장치가 중요하다.
- 거래소별 수수료, 메이커/테이커 구조, 호가 스프레드, 슬리피지, 주문 취소/재호가 비용이 누적되면 방향 예측이 맞아도 실현 손익이 음수가 될 수 있다.
- 분봉 중심 백테스트는 호가 깊이, 부분체결, 주문 지연, 취소 실패, rate limit을 반영하지 못해 성과를 과대평가하기 쉽다.
- LLM이나 단일 예측 모델이 직접 매수/매도를 지시하면 비용과 리스크 게이트를 우회할 위험이 있다.
- 거래소 장애, 시세 지연, 유동성 증발 상황에서 자동 청산을 잘못 실행하면 손실이 확대될 수 있다.

### 현재 대안의 한계

- 단순 시그널 봇은 비용 차감 후 기대값을 거래 전 일관되게 계산하지 않는다.
- 일반 백테스트 도구는 거래소별 주문 정책, 호가 단위, 최소 주문금액, rate limit, 부분체결을 충분히 반영하지 않는 경우가 많다.
- 알림형 도구는 주문 실행과 리스크 정지를 별도 운영자가 수동으로 처리해야 한다.
- LLM 기반 의사결정은 숫자형 예측과 주문 실행 품질 검증에 적합하지 않다.

### 해결하지 않으면 생기는 비용

- 거래 횟수가 늘수록 수수료와 슬리피지가 누적되어 전략 수익률을 잠식한다.
- 백테스트와 실거래 사이의 괴리가 커져 실제 운영 전환 시 손실 가능성이 커진다.
- 장애 상황에서 신규 주문 차단, 주문 취소, 사람 확인 흐름이 없으면 복구가 임의적이고 위험해진다.
- 모호한 전략과 리스크 기준이 누적되면 scope creep이 발생한다.

## 3. 대상 사용자

### Primary user

- 대상: 본인 계정 기준 암호화폐 자동매매 시스템을 직접 개발하거나 운영하려는 개인 개발자 또는 소규모 팀
- 상황: Upbit KRW 현물 paper trading부터 시작해 비용, 리스크, 실행 품질을 먼저 검증하고 싶다.
- 필요한 결과: 비용 차감 후 기대값, 리스크 한도, 주문 실행 기록을 근거로 거래 여부를 판정할 수 있어야 한다.

### Secondary user

- 대상: 퀀트 리서처, 데이터 엔지니어, 운영 담당자
- 상황: 전략 성과를 백테스트, paper trading, 실거래 기록으로 비교하고 싶다.
- 필요한 결과: 전략별 성과, 수수료 비중, 슬리피지, 체결 실패, rate limit 영향을 분해해서 볼 수 있어야 한다.

### 명시적 비사용자

- 투자 자문을 기대하는 최종 투자자
- 검증 없이 AI가 매수/매도를 추천해주기를 원하는 사용자
- 레버리지 선물이나 거래소 간 실시간 차익거래를 MVP에서 바로 운용하려는 사용자

## 4. 목표

- Upbit KRW 현물에서 `KRW-BTC`, `KRW-ETH`를 1차 universe로 검증한다.
- 비용 차감 후 기대값이 동적 안전마진을 넘는 거래만 주문 후보로 통과시킨다.
- Upbit 정책, 수수료, 호가 단위, 최소 주문금액, rate limit을 주문 전 검증한다.
- 리스크 엔진이 전략 신호보다 먼저 작동하도록 한다.
- 백테스트와 paper trading에 수수료, bid/ask 스프레드, 호가 깊이, 부분체결, 주문 지연, 취소 실패, rate limit을 포함한다.
- LLM을 공식 Upbit 공지, 개발자 changelog, 시장경보, 리포트 요약으로 제한하고 직접 매매 판단에서 제외한다.
- 장애 상황에서는 신규 주문 중지, 기존 미체결 주문 취소, 사람 확인 흐름을 기본값으로 둔다.

## 5. 비목표

- MVP에서 선물, 레버리지, 청산 위험이 있는 포지션을 운용하지 않는다.
- MVP에서 거래소 간 실제 자금 이동 기반 차익거래를 구현하지 않는다.
- MVP에서 온체인, 소셜, 뉴스 신호를 자동 주문 트리거로 사용하지 않는다.
- MVP에서 Transformer 계열 딥러닝 모델을 필수 구성요소로 두지 않는다.
- MVP에서 시장가 주문과 실거래 주문 API 호출을 기본 실행 방식으로 두지 않는다.
- MVP에서 법률, 세무, 투자 자문 기능을 제공하지 않는다.
- 거래소 장애 시 자동 청산을 기본 복구 동작으로 두지 않는다.
- MVP에서 출금 API 권한, 입출금 자동화, 타인 계정 연결, 신호 판매를 제공하지 않는다.

## 6. 핵심 사용자 시나리오

### 시나리오 1: 비용 차감 후 거래 후보 선별

1. 사용자가 Upbit KRW paper trading 모드와 `KRW-BTC`, `KRW-ETH` universe를 설정한다.
2. 시스템이 Upbit WebSocket과 REST로 시장 데이터와 정책 스냅샷을 수집한다.
3. 전략이 추세 추종 또는 평균회귀 신호를 만든다.
4. 비용 엔진이 진입 수수료, 청산 수수료, 스프레드 p75, 예상 슬리피지 p95, 취소/재호가 패널티를 차감한다.
5. 비용 차감 후 기대값이 종목군별 safety buffer를 넘지 못하면 주문 후보를 폐기한다.
6. 사용자는 폐기 사유와 차감 항목을 기록에서 확인한다.

### 시나리오 2: 리스크 게이트로 신규 주문 차단

1. 전략이 주문 후보를 생성한다.
2. 리스크 엔진이 일간 손실 -1%, 주간 손실 -3%, 최대 낙폭 -5%, 종목 비중, 알트코인 비중, 유동성, 시세 지연을 확인한다.
3. 기준을 위반하면 신규 주문을 제출하지 않는다.
4. 시스템은 차단 사유, 당시 계정 상태, 시장 상태를 감사 로그에 남긴다.

### 시나리오 3: 지정가 주문 실행과 재호가

1. 주문 후보가 비용과 리스크 게이트를 통과한다.
2. 실행 엔진이 PaperBroker에 가상 지정가 주문을 제출한다.
3. 제한 시간 동안 미체결 또는 부분체결이면 정책에 따라 취소 또는 재호가한다.
4. 체결 후 가상 수수료, 슬리피지, 부분체결 결과를 기록한다.
5. 기록은 백테스트 보정과 전략별 성과 리포트에 반영된다.

### 시나리오 4: 장애 또는 이상징후 대응

1. 시스템이 API 오류, WebSocket 지연, 시세 공백, 거래소 점검 공지를 감지한다.
2. 신규 주문을 중지한다.
3. 기존 미체결 주문을 정책에 따라 취소한다.
4. 자동 청산 대신 사람 확인이 필요한 상태로 전환하고 알림을 보낸다.

## 7. MVP 범위

포함:

- Upbit KRW 현물 `PAPER_TRADING` 모드
- `UpbitKrwSpotAdapter`와 `PaperBroker`
- `KRW-BTC`, `KRW-ETH` 1차 universe
- phase 1.5 알트 수동 편입 기준
- Upbit WebSocket 기반 체결, 호가, 티커 수집
- REST 기반 마켓, 호가 단위, 최소 주문금액, 주문 가능 정책 스냅샷
- UTC/KST 리셋과 24시간 거래대금 피처
- 호가 불균형, 체결강도, 거래대금 급증, 변동성 regime, 스프레드, 슬리피지 추정 피처
- 고유동성 현물 추세 추종 전략
- 고유동성 박스권 평균회귀 전략
- 비용 기반 동적 안전마진 필터
- 계정, 종목, 알트코인, 유동성, 손실, 연속 손실, 인프라 상태 기준 리스크 게이트
- 가상 지정가 중심 주문 실행, 부분체결, 취소, 재호가
- 이벤트 기반 백테스트와 paper trading
- 수수료 비중, 슬리피지, 실현손익, 전략별 성과, 모델 drift 후보 지표
- 공식 Upbit 공지, 개발자 changelog, 시장경보, 일간 리포트에 한정한 LLM 보조 사용
- PostgreSQL + TimescaleDB, DB-backed queue
- Telegram P0/P1/P2/P3 알림

제외:

- 선물 펀딩비 기반 시장중립 실거래
- 김치프리미엄을 이용한 실제 거래소 간 송금/환전 차익거래
- 글로벌 거래소 주문 실행
- 레버리지 사용
- 실거래 주문 API 호출
- 시장가 주문 기본 허용과 신규 진입 시장가
- 온체인, 소셜, 뉴스 기반 자동 주문
- 완전 무인 자동 복구와 자동 청산
- 모바일 앱, 웹 대시보드, 투자자용 리포트 판매 기능
- 출금 API 권한, 입출금 자동화, 타인 계정 연결, 타인 자금 운용, 신호 판매

## 8. 성공 기준

- 모든 주문 후보가 비용 차감 후 기대값 계산 결과와 safety buffer 판정 결과를 가진다.
- 비용 차감 후 기대값이 safety buffer 이하인 주문 후보는 PaperBroker로 제출되지 않는다.
- 모든 주문 제출은 리스크 게이트 승인 기록을 가진다.
- Upbit 정책이 바뀌어도 수수료, 호가 단위, 최소 주문금액, rate limit을 정책 스냅샷 또는 API 응답 기준으로 갱신할 수 있다.
- 백테스트와 paper trading 기록에서 수수료와 슬리피지 비중을 전략별로 분해할 수 있다.
- API 오류 또는 시세 지연 상황에서 신규 주문이 자동으로 중지된다.
- LLM 출력이 직접 주문 명령으로 연결되지 않는다.
- 실거래 주문 API, 출금 API, 선물/레버리지, 거래소 간 송금 경로가 없다.
- 문서화된 acceptance criteria와 테스트 요구사항을 기준으로 구현 issue를 분해할 수 있다.

- [ ] MVP 요구사항은 Upbit KRW 현물, paper trading, `KRW-BTC`/`KRW-ETH`, 추세 추종, 평균회귀, 비용/리스크 게이트로 제한된다.
- [ ] 선물, 거래소 간 실제 차익거래, 레버리지, 뉴스 기반 자동 주문은 MVP 비범위로 명시된다.

  - 비용, 리스크, 실행, 백테스트, LLM 경계가 별도 요구사항으로 분리되어 있는지 확인한다.

## 11. 리스크

- 거래소 수수료, rate limit, 호가 정책은 이벤트나 정책 변경으로 달라질 수 있다.
- 실거래 전환 시 작은 설정 오류가 직접 손실로 이어질 수 있다.
- 낮은 유동성 코인은 백테스트에서 보이는 가격으로 실제 체결되지 않을 수 있다.
- 장애 상황의 자동 청산은 유동성 공백에서 최악의 가격을 만들 수 있다.
- 거래소 이용약관, API 약관, 국내 규제, 세무 기준은 별도 확인이 필요하다.
- 모델 drift나 데이터 품질 저하를 감지하지 못하면 전략 성능이 조용히 악화될 수 있다.
